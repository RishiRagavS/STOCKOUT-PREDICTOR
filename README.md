# 🛒 Stockout Predictor — Context-Aware Inventory Intelligence for Quick-Commerce

## What This Project Does

This system predicts which products are likely to run out of stock and — critically — **explains why**, using real contextual signals. It then delivers that prediction in two different formats to two different audiences simultaneously:

- **Customer-facing message** (shown on the quick-commerce app): A conversational, specific warning that nudges the customer to order now — e.g., *"Umbrellas near you have an 87% chance of running out by evening. Heavy rain is expected and demand has already spiked — order now before stock runs out."*

- **Retailer/warehouse alert** (shown to the store manager): A data-forward operations message — e.g., *"ALERT: SKU-4421 (Umbrellas) — 87% stockout risk. Rain + weekend demand driving spike. Recommend immediate reorder of 200 units."*

The same ML prediction, two completely different framings, for two completely different decision-makers.

## The Problem This Solves

Quick-commerce (10–30 minute delivery) operates on a fundamentally different timescale than traditional retail. A supermarket can afford to run stockout predictions overnight and reorder tomorrow. A Blinkit or Zepto dark store cannot — if umbrellas run out at 4pm on a rainy Friday, that window of revenue is gone forever.

Most existing stockout systems are inward-facing only (they talk to inventory managers, never to customers). This project surfaces the prediction to the end customer as a real-time nudge to purchase, which sits at the intersection of behavioral economics and inventory management.

## Why MongoDB (NoSQL)

This project's data is naturally document-shaped and doesn't fit neatly into relational tables:
- Predictions carry variable contextual snapshots (weather, festival, temporal signals)
- Different product categories have different feature sets
- Alert documents have different schemas than prediction documents
- Time-series sales data has high write frequency and benefits from MongoDB's native time-series collections

MongoDB's time-series collection support (used here for `sales_snapshots`) and flexible document model make it a better fit than a relational DB for this use case.

## Architecture

```
M5 Sales Data (Kaggle)
       ↓
Data Processing → Feature Engineering
       ↓
XGBoost/LightGBM Model
       ↓ predict_proba() → stockout probability (e.g. 0.87)
Context Aggregator
  ├── Day of week / Day of month (payday, weekend signals)
  ├── Indian Festival Calendar (upcoming festivals + affected categories)
  └── Live Weather (OpenWeatherMap API → demand impact mapping)
       ↓
Claude LLM (generates contextual narrative)
       ↓
Two outputs stored in MongoDB:
  ├── predictions collection → customer_message + retailer_alert + context_snapshot
  └── alerts collection (threshold ≥ 70%) → status: unread, for retailer dashboard
```

## A Note on Synthetic Inventory Data

The `generate_inventory.py` script creates simulated inventory snapshots because the M5 Forecasting dataset (Walmart US sales data) does not include actual stock levels — only sales quantities. This is an acknowledged limitation. In a production system, this layer would be replaced by live POS inventory feeds from the dark store's warehouse management system. The synthetic data is a simulation layer that allows the rest of the architecture to be demonstrated end-to-end.

## Data Requirements

Download from the [M5 Forecasting - Accuracy](https://www.kaggle.com/c/m5-forecasting-accuracy) competition on Kaggle:

- `sales_train_evaluation.csv` — daily sales for 30,490 products across 10 stores
- `calendar.csv` — dates, holidays, SNAP days, promotional events

Place both in `data/raw/`.

## Installation & Setup

```bash
# 1. Clone and install
git clone <repo-url>
cd stockout-predictor
pip install -r requirements.txt

# 2. Configure environment
cp .env.example .env
# Fill in: MONGO_URI, ANTHROPIC_API_KEY, OPENWEATHER_API_KEY

# 3. Start MongoDB
mongod

# 4. Run the pipeline (in order)
python scripts/process_data.py
python scripts/generate_inventory.py
python scripts/feature_engineering.py
python scripts/train_model.py
python scripts/seed_mongo.py

# 5. Start the API
cd backend
uvicorn app.main:app --reload
```

## API Endpoints

| Method | Endpoint | Description |
|--------|----------|-------------|
| GET | `/products` | List all products |
| GET | `/inventory/{sku_id}` | Inventory snapshots for a product |
| GET | `/predictions/{sku_id}` | Historical predictions for a product |
| POST | `/predictions` | Generate a new contextual prediction |
| GET | `/alerts` | All unread retailer alerts |
| PATCH | `/alerts/{alert_id}/read` | Mark alert as read |
